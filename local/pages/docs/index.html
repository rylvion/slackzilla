GitHub Pages

static non-functional prototype that serves as a preview of the eventual live platform

The Slackzilla GitHub Pages site is a static prototype designed to preview the visual and structural direction of the eventual live platform, rather than being the actual server-hosted site at rylvion.hackclub.app. It uses a retro hacker-terminal aesthetic across its documentation, API, logs, uptime and admin pages, with the interface designed to resemble a terminal-style control panel for Slackzilla. The source files are organised into separate HTML, CSS, JavaScript and data directories, then processed by a custom Node.js build script that recursively collects the pages, fixes relative paths for the deployed structure, minifies HTML with html-minifier-terser, JavaScript with Terser and CSS with CleanCSS, copies static log data and generates the final dist directory. A small root redirect automatically sends visitors to the logs page, while the resulting static build is automatically deployed to GitHub Pages through GitHub Actions whenever changes reach main or a manual workflow is triggered. This prototype exists primarily to establish the look, navigation and page structure of the platform before the real implementation is built into Slackzilla's server infrastructure.

Manifest Workflow

this registers the commands to the bot (via src/data/commands.json) so it can respond to user interactions.

The workflow triggers on pushes to main or manual dispatch, checks out the repository, installs Node.js and dependencies, then generates and validates the Slack app manifest. It rotates Slack's short-lived manifest token by exchanging the stored refresh token through Slack's tooling.tokens.rotate endpoint, verifies the response, and securely re-encrypts both the new access token and refresh token using GitHub's public key (via libsodium sealed boxes) before updating the repository's encrypted secrets through the GitHub Actions API.

With the fresh access token, it reads manifest.json and performs a signed apps.manifest.update call to Slack, ensuring the manifest is successfully applied by checking the ok field in Slack's response.

Files dependencies

  • .github/workflows/deploy.yml - GitHub Actions workflow to generate, validate, rotate and sync manifest to slack
  • manifest.json - the Slack app manifest file that contains the bot configuration, metadata and commands
  • package.json - Node.js package manifest
  • scripts/generateManifest.js - script to generate AND validate the Slack app manifest
  • scripts/rotateManifestToken.js - script to rotate AND encrypt the Slack app manifest token
  • schemas/ - directory for JSON schemas to validate (currently containing the manifest and the command schema)
  • src/data/commands.json - file containing the command definitions to generate the manifest

Webhook Workflow

this automatically updates the bot with the latest changes of the repository automatically when commits are pushed

Slackzilla's webhook deployment system provides a secure GitHub-to-server CI/CD pipeline where the GitHub Actions workflow constructs a JSON deployment payload containing the repository, branch reference, commit SHA and workflow metadata, then generates an HMAC-SHA256 signature using the shared WEBHOOK_SECRET and sends the payload to the server's /webhook endpoint via an authenticated HTTP POST request. The Node.js webhook server, listening on port 9000, reads the raw request body, extracts X-Hub-Signature-256 and uses the same secret to independently calculate the expected HMAC-SHA256 digest, comparing the signatures with crypto.timingSafeEqual() to prevent timing-based comparison attacks; requests with invalid signatures are rejected with HTTP 401, non-POST requests or unknown paths are rejected, payloads are size-limited to 1 MiB and malformed JSON receives HTTP 400.

After authentication, the server only accepts push events targeting the configured deployment branch, ignoring other event types or branches, and prevents concurrent deployments through an in-memory deployInFlight lock. Once accepted, it immediately returns HTTP 202 and asynchronously executes deploy.sh, which fetches the configured branch, compares the local and remote commit hashes, skips deployment when they match, otherwise hard-resets the working tree to the latest remote commit, installs dependencies with npm ci, and restarts the Slackzilla systemd service, creating an automated chain from GitHub push to authenticated webhook verification, repository synchronisation and production service restart.

  • server/server.js - Node.js webhook server (listens for webhook on port 9000)
  • server/deploy.sh - bash script to fetch, reset, install and restart the Slackzilla service
  • server/slackzilla-webhook.service - systemd service to run the webhook server continuously

Command Handler

this system handles commands and their metadata, registering them to the bot. Without it, the slack bot is non-functional

The Slackzilla command handler uses a data-driven dynamic loading system rather than manually registering every Slack command inside bot.js. At startup, the bot reads src/data/commands.json, iterates through each command definition, validates that its metadata is an object, resolves the referenced JavaScript file inside src/cmds/, checks that the file exists, imports it with require(), and verifies that it exports a function before passing the Slack Bolt App instance and that command's metadata into the module. Each command module is therefore responsible for registering its own Slack command and implementing its behaviour, while commands.json acts as the central source of metadata and configuration. The bot also overrides app.command() with a wrapper that automatically records command usage through the metrics system before handing execution to the command's original handler, with failures in metrics recording isolated from the command itself. This architecture makes commands independently modular and allows new commands to be added by creating a command module and registering its metadata, without turning `bot.js` into a giant collection of command-specific logic.

Files Dependencies

  • src/data/commands.json - JSON file containing the command metadata
  • src/cmds/*.js - directory containing the command modules
  • src/bot.js - main bot file that dynamically loads commands and registers them
  • src/.env - makes the actual bot runs
  • src/utils/*.js - utility functions used by the bot
  • src/meta.js - metadata for the bot
  • server/database/store.js - database store for the bot
